Problema e Objetivos

Fadiga de Alertas (Alert Fatigue)

Equipes de segurança sofrem com silos de informação: AppSec (SAST), Cloud (CSPM) e Infra (Runtime) não se falam.

Objetivo Técnico

Criar um pipeline determinístico (100% rastreável), capaz de deduplicar milhares de alertas de dezenas de ferramentas.

Objetivo de Negócio

Calcular o risco real através de "Combinações Tóxicas" e automatizar fluxos de SLA/Jira.

Origens do Projeto (Sprint 3)

A Prova de Conceito Inicial

O PRIDE nasceu como uma POC focada em provar a viabilidade matemática da priorização de vulnerabilidades (ASPM), usando regras fixas e dados de apenas dois scanners (Semgrep e Nuclei).

Limitações Assumidas no MVP

  • Upload 100% manual de logs via navegador.
  • Ausência de suporte a Contêineres, Nuvem (CSPM) e Runtime.
  • Sem isolamento Multi-tenant (todos viam os mesmos dados) nem migrações (Alembic).
  • Ausência de integração real (a IA gerava o texto para o usuário "copiar e colar" no Jira).

Engenharia de Backend

Service Repository Pattern

O fluxo de dados segue uma estrutura rígida e validada:

Router ➔ Schema (Pydantic) ➔ Service ➔ SQLAlchemy Model ➔ DB

  • Linguagem: Python 3.11+ / FastAPI.
  • Tipagem: mypy --strict (Zero erros tolerados).
  • Linting: ruff (Zero avisos tolerados).
  • Serviços Puros: Lógicas isoladas (normalizer.py, deduplicator.py, risk_engine.py).

Banco de Dados & Isolamento

Row-Level Security (RLS)

O SQLAlchemy mapeia entidades hierárquicas (Tenant ➔ App ➔ Vulnerabilidade ➔ Ticket).

Prevenção de IDOR (Vazamento B2B):

// O isolamento é implementado via evento no ORM // Intercepta TODA query executada no banco: @event.listens_for(Session, "do_orm_execute") def _add_tenant_filter(execute_state): # Injeta automaticamente na query: # WHERE tenant_id = X

Impede que um locatário acesse dados de outro estruturalmente.

Autenticação e RBAC

SSO Corporativo e Provisionamento

  • Login SSO: Suporte a provedores externos (EntraID/Okta simulados).
  • JIT Provisioning (Just-In-Time): O backend extrai o e-mail, cria o usuário/tenant baseado no domínio e devolve um JWT da plataforma.

Controle de Acesso (Middlewares)

  • Admin: Configura SSO e integrações (Jira).
  • AppSec (Manager): Aprova exceções de risco e define Gates.
  • Developer: Visualiza falhas e solicita exceções.

Motor de Ingestão & Scanners (1/2)

Segurança de Código e Supply Chain

Fluxo: Endpoint ➔ Valida Token ➔ Identifica Ferramenta ➔ Transforma Schema.

  • Semgrep (SAST): Lê JSON, extraindo CWE, arquivo e linha (Ex: SQLi).
  • Trivy (SCA & Container): Mapeia vulnerabilidades em dependências (Pip, NPM) e extrai CVE/CVSS.
  • Cosign / Sigstore (Supply Chain): Ingestão de SBOM CycloneDX e validação Keyless (ex: GitHub Actions) para integridade do artefato.

Motor de Ingestão & Scanners (2/2)

Segurança Dinâmica, Nuvem e Runtime

ZAP (DAST)

Mapeia ataques dinâmicos contra endpoints REST ativos.

Prowler (CSPM)

Recebe webhooks de misconfigurations AWS (ex: S3 abertos).

Falco (eBPF)

Alertas de execução em tempo real do kernel Linux.

O PRIDE cruza os sinais para comprovar a explorabilidade:

Risk Engine Determinístico

Decisões sem Alucinação de IA

O cálculo é uma matemática fixa baseada na severidade (CVSS) + modificadores de contexto:

Condição do ContextoImpacto no Score
Ambiente == Produção+ 2
Exposição == Internet+ 2
Flag == REACHABLE (Runtime)+ 3

Classificação final: BAIXO, MÉDIO, ALTO, CRÍTICO.

Risk Engine: Sob o Capô

Matemática Auditável (Regra de Negócio Pura)

1. Base Score (CVSS/Scanner)

O motor ingere a severidade original reportada pela ferramenta (ex: Trivy/Semgrep) e converte para um valor de 0 a 10.

2. Multiplicadores de Contexto

Aplica os pesos de topologia lendo do banco relacional (criticidade_negocio, dados_sensiveis).

// pipeline de cálculo no risk_engine.py def calcular_risco_real(vuln, app_context) -> float: score = map_severity_to_base_score(vuln.severity_bruta) if app_context.is_public: score += 1.5 if app_context.processa_pii: score += 1.0 if vuln.runtime_reachable: score += 3.0 final_score = min(score, 10.0) # Teto matemático return translate_to_pride_risk(final_score)

Regra Inegociável: A Inteligência Artificial (LLMs) não participa, nem influencia esse cálculo. Isso garante 100% de previsibilidade legal e compliance.

Automação de Ticketing

Integração Nativa com Jira

  • Conexão estabelecida via OAuth 3LO usando API v3.
  • Utiliza o ADF (Atlassian Document Format) para criar issues ricas (com tabelas e formatação).
  • Ação automatizada quando um SLA Crítico é acionado, enviando a tarefa direto para o board do desenvolvedor.

Workflow de Remediação

Ciclo de Vida Completo da Vulnerabilidade

O PRIDE automatiza o ciclo, exigindo intervenção humana apenas quando necessário:

  • Auto-Resolução (CI/CD): Se o desenvolvedor corrige o código, o próximo scan fecha o alerta automaticamente via motor de deduplicação.
  • Falsos Positivos: O Dev pode marcar como falso positivo, exigindo evidência/justificativa estruturada (auditada).
  • Exceções de Risco (SLA): Pedido de ampliação de prazo que altera o status para EM_REVISAO, exigindo aprovação manual de um AppSec Manager.
  • Rastreabilidade Total: Todas as ações (quem, quando, o que mudou) são gravadas com assinatura e evento de auditoria.

Inteligência Artificial (Explainer)

Uso seguro de GenAI (GPT-4o)

A IA é usada apenas para gerar resumos legíveis, passos de reprodução e dicas de mitigação. Ela não altera scores de risco.

Data Masking (Privacidade)

Antes do envio, o data_masker.py usa regex para higienizar o payload:

IPs viram: [MASKED-IP] Tokens JWT viram: [MASKED-JWT] Credenciais viram: [MASKED-CREDS]

Garante proteção contra vazamento de PII B2B e Prompt Injection.
